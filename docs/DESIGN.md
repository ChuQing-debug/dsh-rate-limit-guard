# 设计说明

这份文档写给想读代码或改代码的人。使用方法见 [README](../README.md)。

## 整体流程

```
模型请求失败
      │
      ▼
DSH 派发 agent/request-error ──► 限流守护（prepend，先于默认重试策略）
                                      │
                    ┌─────────────────┼──────────────────┐
                    ▼                 ▼                  ▼
               限流 / 额度         刚换上的 Key        其他错误
            RATE_LIMIT、429       被拒绝（401）
            QUOTA、ACCOUNT_QUOTA
                    │                 │                  │
          ┌─────────┴────────┐        ▼                  ▼
          ▼                  ▼   暂停该 Key，          next()
       等待模式           轮换模式  换下一个           交回 DSH
   写 llm/retry         冷却当前 Key
   等待（提示或默认）     选下一个不在冷却的 Key
   写 llm/retry-started  写入目标引用
          │              （全部在冷却：等最早恢复的）
          └─────────┬────────┘
                    ▼
          返回 { kind: 'retry' }，DSH 重试同一步骤
```

监听器的三种返回值：

| 返回 | 含义 |
| --- | --- |
| `{ kind: 'retry' }` | 重试当前步骤 |
| `undefined` | 不重试（等待被中止时用） |
| `next()` 的结果 | 交给后面的处理器，也就是 DSH 的默认重试策略 |

对话里的倒计时行不是插件自己画的：插件往会话里追加 `llm/retry` 和 `llm/retry-started` 两个事件，DSH 的界面本来就会把它们渲染成倒计时。

## 文件

```
index.js      主机端：监听器、配置、轮换、日志、/ratelimit-log 命令
lib.js        纯函数：报错解析、等待时长、选 Key、提供方映射与目录引用
client.js     设置页（React，无构建步骤）
test/         node:test 测试：主机端、纯函数、设置页
docs/         DETAIL.md 是应用内说明；本文件是设计说明
vendor/       内置的 schemastery、cosmokit（MIT）
```

主机端的状态都在 `apply()` 的闭包里，插件卸载时清空：

| 状态 | 内容 |
| --- | --- |
| `attempts` | 每个步骤（会话:轮次:步骤）的重试次数、累计等待时间 |
| `cooldowns` | Key 指纹 → 冷却到什么时候 |
| `rejectedFps` | 被服务商拒绝的 Key 指纹 |
| `lastRotation` | 每个目标引用最近一次轮换：换成了哪个 Key、什么时候、哪个提供方触发的 |
| `logs` | 最近 200 条事件 |

Key 只以 SHA-256 指纹（前 16 位）的形式出现在这些状态里。

## 等待时长

`computeDelay()` 按这个顺序取值：

1. 失败对象里的 `providerRetryAfterMs`（DSH 从 `Retry-After` 响应头得到，但不是所有提供方都会传，见 README 的限制）；
2. `parseRetryHint()` 从报错文字里解析出的时长；
3. 配置的 `waitSeconds`。

然后依次：抬到 `minWaitSeconds` 下限 → 加抖动 → 截到 `maxWaitSeconds`。

### 报错文字的解析

规则是保守的：宁可认不出来走默认时长，也不把别的数字当成等待时长。

- **带单位的时长**（`30s`、`1m30s`、`30 秒`）出现在这些词后面才算：`retry after`、`try again in/after`、`retry in`、`resets in/after`、`available in`、`wait`、`等待`、`稍等`，或者后面跟着"后重试/后再试/后恢复"。
- **不带单位的数字**只在紧跟 `retry after` 时当作秒，并且排除 4xx/5xx（多半是状态码）和大于一天的值（多半是时间戳）。
- **`retry_after_ms`** 这类字段按毫秒算。
- **`until <ISO 时间>`** 和 **`(~9s`** 只在前面有"被限流/被暂缓"之类的词时才算，例如网关返回的 `holding sends until 2026-11-18T11:11:52Z (~9s, exponential backoff)`。

每条规则在 `test/lib.test.js` 里都有正例和反例。

## 轮换

### 选哪个 Key

密钥池的顺序是：`_RLG_ORIGINAL` 备份、`_RLG_PREVIOUS` 备份、然后是配置的轮换池引用（设置页手动填写的独立存储槽）。值相同的引用只算一次，目标引用本身不会进池。其他提供方读取的引用也不能进池：轮换会把目标的值写进槽位，若槽位同时被别的提供方读取，就会互相覆盖；这类引用会被忽略并写进 `/ratelimit-log`。

`pickNext()` 从当前 Key 的下一个开始按顺序找，跳过还在冷却的。都在冷却时返回最早的恢复时间，调用方据此等待。

失败的 Key 冷却多久：

| 失败类型 | 冷却时长 |
| --- | --- |
| 限流 | 和等待时长相同（提示或默认值） |
| 额度/余额耗尽 | `quotaCooldownMinutes` |
| 被服务商拒绝（401） | 1 小时 |

### 并发

目标引用是全局共享的，所以所有轮换排成一个队列执行（`withLock`）。

DSH 不告诉插件"这个失败的请求当时用的是哪个 Key"。几个请求同时在路上时，换完 Key 后还会陆续收到用旧 Key 发出的请求的失败。处理办法是：

- 轮换后 5 秒内，**不是触发这次轮换的步骤**报来的限流失败，先在新 Key 上重试一次，不再轮换。
- 触发轮换的步骤自己再失败，说明新 Key 也被限流了，直接继续轮换。

这是一个基于时间的近似。一个很慢的请求在 5 秒后才失败，会多触发一次轮换，代价是多换一次 Key，不会出错。

### 不轮换的提供方

`resolveRef()` 决定一个提供方的失败该写哪个引用，按顺序：

- `providerRefs` 里有 `提供方=引用` → 用那个引用（手写优先）；
- `提供方=-` 或 `提供方=` → 不轮换；
- 没有手写映射时，查官方提供方目录：`llm.listConfigurableProviders()` 给出每个提供方的
  `settingsNs` 与 `settingsPath`，`settings.describe()` 的 section 值按路径取到 profile，
  profile 的 `apiKeyEnv` 就是这个提供方实际读取的引用；
- `deepseek-account` → 不轮换（内置，目录里也没有 `apiKeyEnv`）；
- 以上都没有 → 用默认的 `credentialRef`。

目录结果缓存 30 秒；读取目录或设置时抛错只会打一条 warn 并退回默认引用，不影响等待逻辑。
设置页的目标选择器用的是同一份目录，再经 `credentials.describe` 过滤掉没有值的提供方；
轮换池则只接受手动引用。之所以不把目录里的引用放进池选择器：轮换会把目标的值写进槽位，
而目录里每个引用都由它自己的提供方读取，写进去会串 Key。主机端会忽略这类引用，并在
`/ratelimit-log` 里标出。

不轮换的提供方按 `fallbackToWait` 走等待或交回。

## 被拒绝的 Key

密钥池里可能有已经失效的 Key。换上它之后请求返回 401，这不是限流错误，原本插件不会处理，于是坏 Key 留在目标引用里，之后所有请求都失败。

现在的处理（`handleRejectedKey` / `replaceRejected`）：

- **只在很窄的条件下接管**：轮换模式、同一个提供方、轮换后 60 秒内、目标引用里仍然是那次轮换写入的 Key。其他情况下的 401 一律交回 DSH，比如你自己的 Key 失效了。
- **403 不算。** 403 通常表示这个 Key 无权使用某个模型或地区，换 Key 没用。DSH 把 401 和 403 都标成 `AUTH`，所以要从报错文字开头的状态码来区分。
- **暂停这个 Key 1 小时，换下一个。** 没有可用的就换回一个没被拒绝的 Key，优先是你的原密钥。
- **有上限。** 同一个引用 10 分钟内最多暂停 2 个。再多说明问题多半不在 Key 上（比如服务商认证服务故障），这时停止暂停，把原密钥换回去。
- **迟到的 401 不会误伤新 Key。** 没有亲自试过新 Key 的步骤报来的 401，先在新 Key 上重试一次。
- **重试次数用完也会清理。** 换掉坏 Key 是清理动作，不占重试次数；次数用完时只换 Key，不再重试。

## 不丢 Key

所有写目标引用的路径（`rotate`、`replaceRejected`、`restoreReady`）都经过 `writeTarget()`，并遵守同一条规则：被覆盖的值必须已经保存在别处。

- 当前值不在密钥池里时，先备份：第一个空的备份位置（`_RLG_ORIGINAL`，然后 `_RLG_PREVIOUS`）。
- 两个位置都有值、或者任何一个读不出来，就拒绝轮换。
- 目标引用读不出来，拒绝轮换。
- 写入前重新读一次目标引用，和轮换开始时不一样就放弃。这是为了不覆盖轮换过程中用户在设置页新保存的 Key。
- 某个提供方的目标引用，不会被当成另一个目标的备用 Key。否则两个目标互相把对方当备份，可能同时覆盖掉同一个 Key。

"读不出来"和"是空的"是分开处理的（`readTarget()` 返回 `{ ok, value }`）。早期版本把读取异常当成空值，会在读取偶发失败时覆盖备份。

## 上限

三道上限，任何一道触发都交回 DSH：

| 上限 | 默认 | 作用 |
| --- | --- | --- |
| `maxAttempts` | 12 | 每个步骤由插件接管的次数 |
| `maxTotalWaitMinutes` | 60 分钟 | 每个步骤累计等待时间；最后一次等待会缩短到剩余额度 |
| `maxWaitSeconds` | 900 秒 | 单次等待 |

## 为什么设置页没有实时状态

DSH 的客户端只能调用构建时就确定的主机能力（见 `@deepseek-ai/dsh-api-remotes` 的说明："Client 不会在运行时发现 Host 中已启用的服务或 Remote 定义"）。第三方插件没法给自己的设置页加一个"读取运行状态"的接口。

设置页用到的都是 DSH 已有的能力：读写配置（`remote.settings`）、查看和保存凭据（`remote.credentials`）、枚举提供方目录（`remote.llm`）。运行状态改由 `/ratelimit-log` 命令输出。
